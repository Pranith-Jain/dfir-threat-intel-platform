# KV Usage Audit — 2026-11-18

Scope: every KV namespace bound to the portfolio Worker (`KV_CACHE`,
`CASE_STUDIES`), the code paths that read/write them, and a migration of the
largest write source off KV. Measured usage comes from Cloudflare's GraphQL
analytics (`kvOperationsAdaptiveGroups`), not from estimates.

**Verdict up front: KV writes are the binding constraint, not reads.** The free
plan allows 1,000 writes/day and `KV_CACHE` averaged 987/day over the window,
with peak days 42-45% above it. Over-quota writes return 429s, which the warm
paths swallow — so slices silently stop refreshing and whole Global Pulse layers
go dark. Reads (100k/day) never came close. The fix is to move cached _data_
off KV and keep KV for what CLAUDE.md says it is for: cross-colo correctness
state (bot offsets, idempotency markers, one-time secrets).

## Measured usage

Window: 2026-10-21 → 2026-11-18 (28 days).

| `KV_CACHE`           | `5125e7…856a` |  76,300 | **27,630** |       0 |     0 |
| `CASE_STUDIES`       | `e6876b…8235` |   9,990 |        640 |      70 | 1,620 |

Measured `put` operations on `KV_CACHE` peaked at **1,450** (2026-11-01),
**1,430** (2026-11-03), and **1,420** (2026-11-16) — 42-45% above the 1,000/day
free-tier cap. The surplus is rejected with 429s, which the warm paths swallow,
so a peak day is also a day where some slices stop refreshing.

Stored data:

| Namespace      |    Size | Keys | Composition                                                   |
| -------------- | ------: | ---: | ------------------------------------------------------------- |
| `KV_CACHE`     |  ~35 MB |  704 | 301 `ais:item:*`, 249 `ogpage:*`, 60 `db:body:*`, warm slices |
| `CASE_STUDIES` | ~8.3 MB |  206 | blog records, images, case-study candidates                   |

`CASE_STUDIES` is not close to a quota on writes (23/day) or reads (357/day).
Its watch item is **lists**: 1,620 over 28 days is only 58/day on average, but
bursts reached ~460/day — 46% of the 1,000/day list cap. Those come from the
case-study admin/cron paths (`storage/approved.ts`, `storage/failed.ts`,
`storage/dedup.ts`, `storage/posts.ts`), not from request traffic, so a single
day with a retry loop or a few manual runs gets close. Left unchanged; flagged
for a pagination/caching pass if it grows.

## Where the writes went, ranked

### 1. Global Pulse warm slices — the dominant source (est. ~500-700/day)

`worker/scheduled.ts` enqueues one queue message per feed every hour
(`enqueueGpFeeds`, gated by `gp:enqueue-cycle` with a 60-minute TTL). The
consumer (`worker/queue-consumer.ts`) fetches the route and writes
`gp:warm:<key>`.

The path already had a write-on-change guard: compare the raw body byte-for-byte
and skip the put when unchanged. But `shouldRefreshWarmKey()` forces a refresh
once the Cache-API marker expires, and the marker's `max-age` is
`ttlSeconds / 3` — 60 minutes for the 180-minute warm TTL, against an hourly
cadence. **That makes the "unchanged" fast path fire roughly once per cycle per
feed**, i.e. ~29 feeds × ~24 cycles ≈ **696 writes/day**, before counting feeds
that genuinely changed. This one path plausibly explains ~70% of the measured
987/day.

It also cost reads: every Global Pulse build read one `gp:warm:<key>` per feed
sequentially — up to 29 KV reads per build. At the DO's rebuild cadence (~96/day;
`REBUILD_THROTTLE_MS = 12 min`) that alone is ~2.8k reads/day, the same order of
magnitude as the _entire_ measured `KV_CACHE` read volume.

### 2. Per-route L2 / last-good writes from the warm self-fetch

Each warmed route is fetched through its own handler, and most handlers persist
a last-good copy. Default `writeLastGood` is debounced 6h (≈4 writes/key/day ×
~29 routes ≈ **116/day**), but several cron warms pass `force: true` and wrote
on every tick:

- `warmCveRecentCache` — 24/day _(now guarded)_
- `warmCveDigestCache` — 24/day _(now guarded)_
- `warmRansomwareRecentCache` — 24/day _(now guarded)_
- `warmPromptintelCache` — 24/day _(now guarded)_
- `refreshVictimReleaksCache` — 4/day, `hour % 6 === 3` _(now guarded)_

### 3. Global Pulse response / last-good keys

`gp:response:v3` and `gp:last-good:v1` are written by successful rebuilds. The
response key already had a write-on-change guard in the request path, but the
last-good write did not — a rebuild producing identical bytes still paid a
write. Up to ~24/day at the cron cadence, and more whenever the DO rebuilds in
process (its 12-minute throttle allows up to ~120/day).

### 4. Daily briefs sync

`worker/lib/daily-briefs-sync.ts` runs every 6h. It writes one KV body per brief
type (6 types × 4 runs = **24/day**) and rewrote the index unconditionally even
when every body was byte-identical — **4/day** of pure `generatedAt` churn.

### 5. Everything else

`phishing-fingerprint` (write-on-scan), `radar` (scan results), GHSA/landscape
metadata syncs, RAG "seen" markers, and the snapshot warm path
(`shouldWriteLastGood`-debounced). Also the CyberPulse source warm
(`cp:warm:x_accounts`, enqueued every 30 min; its 50-minute refresh marker means
an unchanged payload is rewritten about hourly ≈ **24/day**) and the
content-hash-keyed `ais:item:*` summaries (write-once per unique item,
bounded by new items/day). Collectively small, but `radar` and
`phishing-fingerprint` are unbounded by design, so they are worth keeping in
mind if writes ever creep back up.

## Changes shipped

### Warm slices move from KV to D1

- `migrations/0059_warm_slices.sql` — `warm_slices(key, body, updated_at,
expires_at)` + expiry index. Expiry is a column, not a TTL: a stale row is
  just a read miss, so no delete job and no delete quota.
- `api/src/lib/warm-slices.ts` (new) — `readWarmSliceRaw`, `readWarmSlice`,
  `readWarmSlices`, `writeWarmSlice`. D1 is canonical; KV is the fallback for a
  missing table (migration not yet applied), a D1 error, or a body over the ~1 MB
  row limit (cutoff 900k chars). Bodies are stored verbatim so the existing
  write-on-change guard stays a literal byte comparison.
- `readWarmSlices` is **one batched indexed query** (chunked at 50 keys) with a
  single batched KV `get(keys[])` only for keys D1 did not return. That is the
  budget win: the Global Pulse build's worst case drops from 43 to 17
  subrequests (`BUDGET_MAX = 44`), so the tail of `GP_FEEDS` is no longer
  deterministically dropped when the budget runs out.

Call sites converted:

| File                                     | Before                                  | After                                 |
| ---------------------------------------- | --------------------------------------- | ------------------------------------- |
| `worker/queue-consumer.ts`               | `kv.get`/`kv.put` on `gp:warm:*`        | `readWarmSliceRaw` / `writeWarmSlice` |
| `api/src/routes/global-pulse/handler.ts` | sequential per-feed `readKvJson`        | one `readWarmSlices` call             |
| `worker/scheduled.ts`                    | 3 KV gets/bulk gets                     | `readWarmSlice` / `readWarmSlices`    |
| `api/src/routes/snapshot.ts`             | `kv.get('gp:warm:telegram')` + `kv.put` | `readWarmSlice` / `writeWarmSlice`    |

### Write-on-change guards

- `api/src/lib/kv-write.ts` (new) — `kvPutIfChanged(kv, key, body, opts)`.
  Compares the stored **raw text** (re-serializing can reorder keys and turn
  every rebuild into a spurious write). `refreshAfterSeconds` refreshes the TTL
  at most once per window via the free per-colo Cache API, so an unchanged value
  cannot expire just because the producer kept skipping writes.
- `api/src/lib/lastgood.ts` — `writeLastGood` gains `skipIfUnchanged`, which
  still refreshes the per-colo shadow but skips the KV put on byte-identical
  payloads.
- `api/src/routes/cve-recent.ts`, `api/src/routes/cve-digest.ts` — hourly warms
  use `kvPutIfChanged` with a 6h TTL refresh.
- `api/src/routes/ransomware-recent.ts`, `api/src/routes/promptintel.ts`,
  `api/src/routes/victim-releaks.ts` — `force: true` + `skipIfUnchanged`. The
  force flag still bypasses the request-path debounce; only the redundant put is
  skipped.
- `api/src/routes/global-pulse/handler.ts` — the GP last-good write now does one
  raw read that serves both the layer-count comparison and the byte comparison
  (it previously did two reads in a row), and skips the put on identical bytes.
- `worker/lib/daily-briefs-sync.ts` — the index is written only when a body was
  written, the index is absent/malformed, or the entry count changed.

### Policy + tests

- `eslint-rules/kv-policy.js` — allowlists `api/src/lib/kv-write.ts` and
  `api/src/lib/warm-slices.ts` (both intentionally encapsulate raw KV access).
- `api/test/lib/warm-slices.test.ts` (new) — D1 hit, KV fallback, expiry,
  batching, oversize-body fallback. The local miniflare DB has no migrations, so
  the test creates the table itself.
- `api/test/lib/lastgood.test.ts` — three cases for `skipIfUnchanged`: identical
  bytes skip the put, changed bytes write, absent value writes.
- `api/test/routes/snapshot-telegram-warm.test.ts` — updated for the
  `WarmSliceEnv` signature with a realistic KV fake.

## Expected effect

Measured writes were 987/day average, peaks 1,450. Modelled post-change:

| Source                             |          Before |                          After |
| ---------------------------------- | --------------: | -----------------------------: |
| GP warm slices (KV)                |        ~500-700 |                     **0** (D1) |
| GP response + last-good            |            ~48+ |   ≤ 48, minus unchanged builds |
| CVE / ransomware hourly warms      |             ~72 | ~0 on quiet hours (6h refresh) |
| PromptIntel + victim-releaks warms |             ~28 |               ~0 on quiet days |
| Daily briefs                       |             ~28 |          ~24 bodies + ~0 index |
| Per-route debounced last-good      |            ~116 |                           ~116 |
| Other (radar, phishing, syncs)     |       remainder |                      remainder |
| **Total**                          | **987/day avg** |               **~250-400/day** |

That is roughly **60-75% fewer KV writes**, which puts the account back under
1,000/day with headroom instead of at 99% of it. Reads drop by roughly the
Global Pulse build rate × 29 — several thousand/day, most of the measured 2,725.

These are modelled from code paths and cadences, not yet measured. The follow-up
is to re-run the same GraphQL query after 3-7 days and confirm the write line
actually lands in the 250-400 range (see Verification).

## Alternatives considered

- **R2** — the natural fit for "big cached bodies" and it would also fix the
  900k-char KV fallback. Rejected: R2 is not enabled on this account
  (`10042 Please enable R2`). Revisit if it is turned on; `warm-slices.ts` is the
  one place that would change.
- **Durable Object storage** — already exists for Global Pulse, but the DO is a
  single instance and the warm slices are shared read-mostly data. Using DO
  storage would serialize all reads through one object and add latency to every
  colo's build for no quota benefit at this size.
- **Cache API only** — free and fast, but per-colo. The whole point of the warm
  slices is that a cold colo can serve data warmed elsewhere; dropping the
  cross-colo leg would blank layers until each colo rebuilt. Kept as the L1
  shadow in front of D1, not as the store.
- **Keep KV, just slow the cadence** — the simplest change, but it trades
  freshness for quota and still sits near the cliff during a burst. D1 removes
  the constraint instead of rationing it. Cadence was left alone (hourly warm,
  180-minute TTL) because freshness is the product.
- **D1 for everything** — not appropriate. Bot offsets, idempotency markers, and
  one-time secrets need KV's cross-colo read-after-write semantics; D1 has a
  single primary and would add latency and contention to hot correctness paths.

## Rollout and verification

Deploy order is safe in either direction: the Worker falls back to KV whenever
`warm_slices` is missing, and the reverse (table exists, old code running) is
inert. Apply the migration:

```sh
npx wrangler d1 migrations apply pranithjain-briefings --remote
```

Legacy `gp:warm:*` KV keys keep their TTLs and serve as the read fallback until
they expire (≤ 3h after cutover). No cleanup step.

Verified locally:

- `npm run typecheck:api` — pass
- `npm run typecheck:worker` — pass
- `npx eslint` on all changed source files with `--max-warnings 0` — pass
- Focused regression run (8 files, 73 tests) — pass:
  `test/lib/warm-slices.test.ts`, `test/lib/lastgood.test.ts`,
  `test/queue-consumer.test.ts`, `test/routes/global-pulse-build.test.ts`,
  `test/routes/cve-recent.test.ts`, `test/routes/cve-digest.test.ts`,
  `test/routes/ransomware-recent.test.ts`,
  `test/routes/snapshot-telegram-warm.test.ts`

## Open items

1. **Per-route debounced last-good writes (~116/day)** are the next largest
   bucket. They are already debounced; lowering the debounce would hurt
   stale-if-error quality, so leave them unless the numbers say otherwise.
2. **`CASE_STUDIES` list bursts (~460/day peak)** are under the cap but close
   enough to watch. If it grows, page or cache the index reads in
   `storage/posts.ts` / `storage/approved.ts`.
3. **GP warm cadence** (`GP_ENQUEUE_CYCLE_TTL_SECONDS = 60 * 60`) was
   deliberately not changed. With warm slices on D1 the marginal cost of the
   hourly cycle is a handful of D1 rows, not KV writes.
4. **CyberPulse `cp:warm:x_accounts` (~24/day)** is now the largest single
   remaining warm write. It can move to the same `warm_slices` store under a
   distinct key (e.g. `cp:x_accounts`) with a one-line change in
   `worker/queue-consumer.ts` plus the two read sites in `worker/scheduled.ts`.
