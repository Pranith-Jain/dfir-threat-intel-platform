The CyberView Scanner

Find known-vulnerable software on your own network and see what to patch first. The scanner reads the version each service states about itself, matches it against CISA's known-exploited flaws and NVD's affected-version ranges with the same code as the Vulnerabilities page, and ranks what it finds by the CyberView rating, every point listed. Nothing is uploaded: results stay in a folder on your machine.

Get the scannerRead the guide and what it sendsImport results into My software

Only scan systems you own, or systems whose owner has given you written permission to test. Scanning other people's systems without permission may be unlawful. The scanner will not start until you list your targets in a scope file and attest there that you are authorized; it prints your attestation and scope at the start of every run and writes them into the report.

Loading the scanner's numbers

Counted by a script from the scanner's own code at every build of this site, not written by hand. Products are distinct vendor and product names (NVD's names) its fingerprints can report. Rules are its built-in banner, header and certificate entries plus the detection rows its fingerprint modules build. Known-exploited coverage compares those names with the products in CISA's KEV catalog on file here, by name only: it is approximate, and a product it can name may still state no version. The path rail is off by default; a dash means that part is not in this release.

What it checks

Everything below comes from what a service sends on its own or in answer to one ordinary request. Each area says what it reads and what it never does.

Services and versions

Greetings that SSH, FTP, mail, MySQL and VNC servers send by themselves, the web server's headers on one request for the root page, and the TLS certificate from one handshake.

Never sends crafted input or follows redirects; one request for "/" per web port.

Edge appliances

VPN gateways, firewalls, load balancers, routers, cameras and NAS that CISA lists as known exploited, named from the page title, a few fixed page markers, headers, the login realm, the greeting or the certificate issuer the scan already has.

Never adds a request, a path or a login to identify them.

CMS, plugins and JavaScript libraries

Versions a site discloses in its own root page: generator tags, versioned script file names, library banners and CDN paths.

Never fetches a script, a plugin file or a folder, and uses no wordlist.

Application consoles

Management and application consoles recognised from the same root-page response the scan already collected.

Never logs in or submits a form.

TLS and certificate hygiene

Expired, expiring or not-yet-valid certificates, self-signed ones, weak keys and signatures, a name that does not match, old protocols, weak ciphers, weak Diffie-Hellman and no forward secrecy.

Reads the one handshake it made; never enumerates protocols or ciphers.

HTTP and mail hygiene

Missing or weak security headers, cookie flags, an open CORS policy, redirects, default, setup and debug pages, and mail or logins offered without encryption.

Never sends an extra request; keeps cookie names only, never their values or page text.

SSH key exchange

The algorithms an SSH server offers in the packet it sends right after its banner, on the same connection: a weak set is flagged, post-quantum key exchange is noted.

Never starts a key exchange or logs in.

UDP: DNS, NTP and SNMP

opt-in: --udp

One read-only datagram per service per host: the resolver's stated version, ntpd's version string, and SNMP's system description with the standard read community "public" only.

Never tries another community, walks or writes, or retransmits.

Finding the hosts for you

opt-in: scope file

Sweeps your attested ranges, resolves your own domains and their Certificate Transparency names, imports an asset list, or reads the cloud inventory JSON your own read-only command printed.

Never widens your scope: every host found is re-checked against it. Never runs your cloud CLI or reads your keys.

HTTP path rail

A frozen table of reviewed version paths, asked only for a product the root page already pointed to, with a small fixed number of extra requests per host.

Off by default; no logins, management or exploit paths, and no paths you supply.

What it will never do

  • Exploit anything: no payloads, injection strings or crafted input, and no check that works by triggering a flaw.
  • Log in, guess or test passwords, test SNMP community strings, capture or crack hashes.
  • Use path, plugin or password wordlists.
  • Flood or amplify: polite rate limits you can lower but never raise, and no mode that removes them.
  • Hide what it is: no spoofed addresses, stealth or fragmented packets, or disguised User-Agent. It names itself in its requests and its SSH identification.
  • Touch anything outside your scope file, or sweep public address space: public addresses need an extra confirmation and stay under a hard cap.
  • Run your cloud CLI, or read or store your cloud or API keys.
  • Upload anything: no findings, scope, addresses or telemetry. No AI model runs in it.

How to run it

Needs Node.js 22 or later and a copy of the CyberView repository; nothing else to install. Run from the repository's folder. A single-file version is on the repository's Releases page; check it with its SHA256SUMS and with gh attestation verify cyberview-scan-<version>.mjs --repo xanderhutch/CyberView, which shows it was built by this repository's release workflow and not swapped afterwards.

  1. Write a scope file: build one on this page, or start one from the command line
    node scanner/cyberview-scan.mjs init --out scope.json
  2. Edit scope.json: owner, contact and targets; set attestation.agreed to true and attestation.name to your name. Then check it (nothing is scanned)
    node scanner/cyberview-scan.mjs check --scope scope.json
  3. Scan, reading CyberView's public data
    node scanner/cyberview-scan.mjs scan --scope scope.json --online

No internet on that network? Run node scanner/cyberview-scan.mjs data --out cyberview-data on a connected machine, carry the folder across, and scan with --data cyberview-data instead of --online. Exit code 0 means clean and complete, 2 means some hosts or ports could not be checked, 3 means the scan stopped early.

Tools that run in this page

Both tools below work entirely in your browser. A report you open is read by this page's own script and is never uploaded, sent or stored: close the tab and it is gone. A scope file is built here and saved by your browser as a download. Nothing goes to CyberView or anyone else.

View a scan report

Open one or more report.json files from the scanner's output folder. You see the run and its authorization, the headline counts, every finding with its rating points, the hosts, certificates, observations and what the scan could not see. Open two or more to see what changed between scans, with the same rules as the scanner's --compare.

Build a scope file

Only list systems you own, or systems whose owner has given you written permission to test. Scanning other people's systems without permission may be unlawful. The scanner reads this file before it sends anything, refuses to start without your attestation, prints it at the start of every run and writes it into the report.

Private ranges (10/8, 172.16/12, 192.168/16, loopback, link-local, IPv6 fc00::/7) run with the scope file alone. A public address also needs --i-am-authorized-for-public-ranges on the command line; a public IPv4 range may be no wider than a /24, and one scan touches at most 1,024 public addresses, whatever the file says.

I own the systems listed in targets, or I hold written permission from their owner to scan them for known vulnerabilities, and this scan stays within that permission.

The file is checked here with the same rules as the scanner's own check command; run that command too, since it is the scanner that decides. Discovery options (domains, Certificate Transparency, asset lists, cloud inventory) can be added to the file by hand: see the guide.
